# schema.md — ISMS Database Schema

**Source of truth for structure: the class diagram.** Source of truth for *which stores exist and how data flows*: the DFD (D1–D8 map 1:1 to classes). SRS Appendix A (data dictionary) is used only to resolve enumerations and meanings.

Database: **PostgreSQL 16**. All names `snake_case`. All timestamps `TIMESTAMPTZ`. The DDL in §2 is copied verbatim into Flyway `V1__init.sql`; JPA entities use explicit `@Table`/`@Column` names and Hibernate runs with `ddl-auto=validate`.

## 1. Class → Table → DFD store mapping

| Class diagram class | Table | DFD store | Notes |
|---|---|---|---|
| User (+ Manager, WarehouseStaff, Administrator, SalesPersonnel) | `users` | D1 | Single-table inheritance. Subclasses are values of `role`. |
| Supplier | `suppliers` | D2 | |
| Product | `products` | D3 | |
| StockRecord | `stock_records` | D4 | Composite PK (`sku_id`, `location_id`) |
| SalesOrder | `sales_orders` | D5 | |
| Forecast | `forecasts` | D6 | Composite PK (`sku_id`, `location_id`, `forecast_period`) |
| PurchaseOrder | `purchase_orders` | D7 | |
| Notification | `notifications` | D8 | |
| (list attribute `line_items` of PurchaseOrder) | `po_line_items` | — | Realises the `Product * — 1..* PurchaseOrder` "contains" association |
| (list attribute `line_items` of SalesOrder) | `sales_order_line_items` | — | Realises the `Product 1..* — * SalesOrder` "contains" association |

No other tables. No `invoices` table: an invoice is a PDF generated by `SalesOrder.generate_invoice()` and stored on disk at `storage/invoices/{order_id}.pdf`.

## 2. DDL

```sql
-- D1 User  (class: User; subclasses = role values)
CREATE TABLE users (
  user_id          VARCHAR(32)  PRIMARY KEY,
  name             VARCHAR(120) NOT NULL,
  email            VARCHAR(255) NOT NULL UNIQUE,
  role             VARCHAR(20)  NOT NULL
                   CHECK (role IN ('Administrator','Manager','Warehouse Staff','Sales Personnel')),
  hashed_password  VARCHAR(255) NOT NULL,          -- BCrypt hash
  status           VARCHAR(10)  NOT NULL DEFAULT 'active'
                   CHECK (status IN ('active','inactive','locked'))
);

-- D2 Supplier
CREATE TABLE suppliers (
  supplier_id          VARCHAR(32)  PRIMARY KEY,
  name                 VARCHAR(160) NOT NULL,
  contact_details      TEXT         NOT NULL,        -- phone/email/address block
  rating               NUMERIC(3,2) NOT NULL DEFAULT 0 CHECK (rating BETWEEN 0 AND 5),
  lead_time            INTEGER      NOT NULL DEFAULT 0 CHECK (lead_time >= 0),  -- days
  procurement_history  TEXT         NOT NULL DEFAULT '',
  is_active            BOOLEAN      NOT NULL DEFAULT TRUE      -- DEVIATION D-1
);

-- D3 Product
CREATE TABLE products (
  sku_id           VARCHAR(32)   PRIMARY KEY,
  name             VARCHAR(160)  NOT NULL,
  category         VARCHAR(80)   NOT NULL,
  unit_price       NUMERIC(12,2) NOT NULL CHECK (unit_price >= 0),
  reorder_point    INTEGER       NOT NULL DEFAULT 0 CHECK (reorder_point >= 0),
  unit_of_measure  VARCHAR(20)   NOT NULL
);
CREATE INDEX ix_products_category ON products(category);

-- D4 StockRecord   (Product 1 —tracked— 1..* StockRecord)
CREATE TABLE stock_records (
  sku_id             VARCHAR(32) NOT NULL REFERENCES products(sku_id) ON DELETE RESTRICT,
  location_id        VARCHAR(32) NOT NULL,
  quantity_on_hand   INTEGER     NOT NULL DEFAULT 0 CHECK (quantity_on_hand >= 0),   -- BR-3
  quantity_reserved  INTEGER     NOT NULL DEFAULT 0 CHECK (quantity_reserved >= 0),
  last_updated       TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (sku_id, location_id),
  CHECK (quantity_reserved <= quantity_on_hand)
);

-- D6 Forecast      (Product 1 —analyzed— 0..* Forecast)
CREATE TABLE forecasts (
  sku_id                    VARCHAR(32) NOT NULL REFERENCES products(sku_id) ON DELETE CASCADE,
  location_id               VARCHAR(32) NOT NULL,
  forecast_period           VARCHAR(16) NOT NULL,   -- e.g. '2026-11' or '2026-W45'
  predicted_demand          INTEGER     NOT NULL CHECK (predicted_demand >= 0),
  recommended_reorder_qty   INTEGER     NOT NULL CHECK (recommended_reorder_qty >= 0),
  PRIMARY KEY (sku_id, location_id, forecast_period)
);

-- D7 PurchaseOrder (Supplier 1 —fulfills— 0..* PO; Manager 1 —approves— 0..* PO; WarehouseStaff 1 —receives— 0..* PO)
CREATE TABLE purchase_orders (
  po_id               VARCHAR(32) PRIMARY KEY,
  supplier_id         VARCHAR(32) NOT NULL REFERENCES suppliers(supplier_id),
  status              VARCHAR(20) NOT NULL DEFAULT 'Draft'
                      CHECK (status IN ('Draft','Pending Approval','Approved',
                                        'Partially Received','Received','Cancelled')),
  order_date          DATE        NOT NULL DEFAULT CURRENT_DATE,
  expected_date       DATE        NOT NULL,
  manager_id          VARCHAR(32) REFERENCES users(user_id),   -- "approves" association (owning Manager)
  warehouse_staff_id  VARCHAR(32) REFERENCES users(user_id)    -- "receives" association (last receiver)
);
CREATE INDEX ix_po_status ON purchase_orders(status);

CREATE TABLE po_line_items (
  po_id              VARCHAR(32) NOT NULL REFERENCES purchase_orders(po_id) ON DELETE CASCADE,
  sku_id             VARCHAR(32) NOT NULL REFERENCES products(sku_id),
  quantity_ordered   INTEGER     NOT NULL CHECK (quantity_ordered > 0),
  quantity_received  INTEGER     NOT NULL DEFAULT 0 CHECK (quantity_received >= 0),
  last_received_at   TIMESTAMPTZ,                -- used for on-time-rate (Supplier.track_performance)
  PRIMARY KEY (po_id, sku_id),
  CHECK (quantity_received <= quantity_ordered)
);

-- D5 SalesOrder
CREATE TABLE sales_orders (
  order_id           VARCHAR(48)  PRIMARY KEY,         -- marketplace order id is reused => webhook idempotency
  channel            VARCHAR(40)  NOT NULL,            -- 'physical' | 'storefront' | 'marketplace:<name>'
  customer_info      TEXT         NOT NULL DEFAULT '',
  status             VARCHAR(12)  NOT NULL DEFAULT 'Pending'
                     CHECK (status IN ('Pending','Confirmed','Completed','Cancelled','Returned','Rejected')),
  payment_reference  VARCHAR(80),
  created_at         TIMESTAMPTZ  NOT NULL DEFAULT now()    -- DEVIATION D-2
);
CREATE INDEX ix_sales_channel_date ON sales_orders(channel, created_at);

CREATE TABLE sales_order_line_items (
  order_id    VARCHAR(48)   NOT NULL REFERENCES sales_orders(order_id) ON DELETE CASCADE,
  sku_id      VARCHAR(32)   NOT NULL REFERENCES products(sku_id),
  location_id VARCHAR(32)   NOT NULL,
  quantity    INTEGER       NOT NULL CHECK (quantity > 0),
  unit_price  NUMERIC(12,2) NOT NULL,                 -- price snapshot for invoice
  PRIMARY KEY (order_id, sku_id)
);

-- D8 Notification  (User 1 —receives— 0..* Notification; one row per recipient+channel)
CREATE TABLE notifications (
  notification_id  VARCHAR(40)  PRIMARY KEY,
  user_id          VARCHAR(32)  NOT NULL REFERENCES users(user_id),
  type             VARCHAR(20)  NOT NULL
                   CHECK (type IN ('Low Stock','Shipping Delay','Order Update','Other Alert')),
  channel          VARCHAR(10)  NOT NULL CHECK (channel IN ('E-mail','SMS','Audio')),
  message          TEXT         NOT NULL,
  timestamp        TIMESTAMPTZ  NOT NULL DEFAULT now(),
  status           VARCHAR(12)  NOT NULL DEFAULT 'Pending'
                   CHECK (status IN ('Pending','Sent','Failed'))
);
CREATE INDEX ix_notif_user ON notifications(user_id, timestamp DESC);
```

## 3. Deviation register (needs your sign-off; kept to the absolute minimum)

| # | Deviation | Why it is unavoidable | If you reject it |
|---|---|---|---|
| D-1 | `suppliers.is_active` | `Administrator.deactivate_supplier()` and `Supplier.Deactivate` exist in the class diagram/SRS, but `Supplier` has no status attribute. | Make `deactivate_supplier()` a guarded hard delete (only if the supplier has zero POs). |
| D-2 | `sales_orders.created_at` | `Sales.Order.View` filters by date range and `Analytics.Dashboard.Revenue` aggregates by time period; `SalesOrder` has no date. | Revenue/date filters become impossible; drop those two features. |
| D-3 | Junction tables `po_line_items`, `sales_order_line_items` (+ columns `quantity_*`, `unit_price`, `location_id`, `last_received_at`) | `line_items: List` cannot be a relational column; the many-to-many "contains" associations require them. | Not possible in a relational DB (SRS CO-2). |

Everything else listed in the class diagram is stored exactly as drawn. Items the SRS needs that have **no** schema impact by design:

- **Failed-login lockout** (`Auth.Login.Fail`): counter held in an in-memory TTL cache, lock sets `users.status='locked'`.
- **PO rejection reason** (`PO.Approve.Reject`): delivered as a `notifications` row of type `Order Update` to the owning Manager.
- **Approval limit / supplier credit limit** (`PO.Approve`, BR-2): environment configuration (`APPROVAL_LIMIT_MANAGER`, `SUPPLIER_CREDIT_LIMIT`).
- **Audit log** (`Auth.Audit.Log`, SE-5): structured JSON application log file; **not** a table. Optional upgrade to a table only with your approval.
- **Notification preferences** (`Notify.Preferences.Configure`): deferred, would need a new table/column.

## 4. Enumerations (from SRS Appendix A)

- `users.role`: Administrator | Manager | Warehouse Staff | Sales Personnel
- `purchase_orders.status`: Draft | Pending Approval | Approved | Partially Received | Received | Cancelled (SRS §4.4 and data dictionary; the second PO diagram in Appendix B with Sent/Confirmed/Closed conflicts with the SRS text and is **not** used)
- `notifications.type`: Low Stock | Shipping Delay | Order Update | Other Alert
- `notifications.channel`: E-mail | SMS | Audio

## 5. Relationship cardinalities (class diagram)

| Association | Cardinality | Implementation |
|---|---|---|
| Product tracked StockRecord | 1 — 1..* | FK `stock_records.sku_id`; product creation also creates ≥1 stock record |
| Product analyzed Forecast | 1 — 0..* | FK `forecasts.sku_id` |
| Product contains PurchaseOrder | * — 1..* | `po_line_items` |
| Product contains SalesOrder | 1..* — * | `sales_order_line_items` |
| Supplier fulfills PurchaseOrder | 1 — 0..* | FK `purchase_orders.supplier_id` |
| Manager approves PurchaseOrder | 1 — 0..* | FK `purchase_orders.manager_id` |
| WarehouseStaff receives PurchaseOrder | 1 — 0..* | FK `purchase_orders.warehouse_staff_id` |
| User receives Notification | 1 — 0..* | FK `notifications.user_id` |

## 6. Concurrency & integrity rules (DB level)

- All stock mutations run in one transaction using `SELECT … FOR UPDATE` on the `stock_records` row. This implements `Sync.Channel.Conflict` (first confirmed transaction wins, loser gets an out-of-stock error) and BR-3.
- `CHECK` constraints above are the last line of defence; services must validate first and return friendly errors.
- IDs are generated by the application as prefixed strings: `USR-0001`, `SUP-0001`, `PO-2026-0001`, `ORD-…`, `NTF-…`. SKU IDs are user-supplied.
